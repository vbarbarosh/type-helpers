## Verdict

The library is in very good shape: small, dependency-free, fully covered,
and its documentation is executable and accurate. Nothing found is a
security issue, and nothing breaks the documented happy path. The findings
below are (1) three places where the "total normalizer" promise leaks —
sparse-array holes, half-honored modifiers in shorthand objects, and
prototype-chain property reads — (2) several schema errors that surface as
unhelpful `TypeError`s, and (3) an `engines` claim (`>=18`) the test script
and CI no longer back. Everything else is hygiene.

## Findings

Severity is about impact on the library's own contract (well-typed,
idempotent output; data never throws), not exploitability.

### M1. `array` lets sparse-array holes through

`Array.prototype.map` skips holes, so the `array` type reproduces them:

```js
make([,,], {type: 'array', of: 'int'})     // [ <2 empty items> ]
0 in make([,,], {type: 'array', of: 'int'}) // false
JSON.stringify(...)                         // '[null,null]'
make({a: [,1]}, {a: {type: 'array', of: 'int'}}).a // [ <1 empty item>, 1 ]
```

The output is neither well-typed (holes read as `undefined`, `forEach`/`map`
skip them) nor a fixed point (`make(make([,,], e), e)` yields a different
value). `tuple` handles the same input correctly (`[0, 0]`) because it
indexes explicitly; `tags` is unaffected. `[,,]` is in `edge_values`, but
`make.test.js` only sweeps scalars, so this is not pinned.

Fix: `Array.from(input, v => make(v, conf.of, types))` (Array.from visits
holes as `undefined`). Then add `[,,]` and `[,1]` cases to the `array`
section.

Source: `src/make.js:89`.

### M2. Reserved modifiers inside props-shorthand objects are half-honored

README defines an object without `type` as `{type: 'obj', props: expr}`, so
`nullable`/`before`/`after`/`optional` there should be plain prop names. In
practice `make_impl` checks `expr.nullable` *before* deciding the object is
shorthand (`src/make.js:227`), which makes the outcome depend on the input:

```js
make(null, {nullable: true, a: 'int'}) // null           (modifier honored)
make({},   {nullable: true, a: 'int'}) // throws Error: Invalid expression: true
make({},   {before: v => v, a: 'int'}) // {before: undefined, a: 0}   (silently a prop)
make({},   {x: {a: 'int', optional: true}})   // {}   (optional honored)
make({x: {}}, {x: {a: 'int', optional: true}}) // throws Error: Invalid expression: true
```

The first pair is a data-dependent throw, which the library otherwise
reserves for unions without a default ([shape.md](shape.md)). The `optional`
cases show a second gap: `obj` reads `v?.optional` off the raw expression
(`src/make.js:134`), so `optional` *is* a reserved word, yet it is missing
from the README's reserved-property table and the `type: [...]` escape
hatch does not strip it:

```js
make({x: {}}, {x: {type: ['str'], optional: true}}) // throws Error: Invalid expression: true
```

Fix (pick one policy and pin it):

- *Strict*: move the `nullable` short-circuit below the shorthand branch so
  shorthand objects never see modifiers, and document that `nullable`,
  `before`, `after`, `optional` require the explicit `{type: 'obj', ...}`
  form. Simplest and matches the README table as written.
- *Lenient*: treat `nullable`/`before`/`after`/`optional` as modifiers in
  shorthand too (destructure them out the way the escape hatch does), and
  add `optional` to the escape-hatch destructuring and to the README table.

Either way, add `optional` to the reserved-property table.

### M3. `obj` and `union` read input properties through the prototype chain

`value_obj[k]` and `input?.[prop]` are ordinary reads, so a schema prop named
like an `Object.prototype` member picks up the inherited value when the
input lacks its own:

```js
make({}, {constructor: 'raw'})              // {constructor: [Function: Object]}
make({}, {hasOwnProperty: v => typeof v})   // {hasOwnProperty: 'function'}
make({}, {toString: {type: 'str', optional: true}}) // {toString: ''} — optional not omitted
```

Coercing types (`str`, `int`, `obj`, …) neutralize the leak, so this only
bites with `raw`, `any`, or function types, and only for a handful of prop
names — but "untrusted in, well-typed out" should not depend on that. The
same read path also means live objects with throwing getters or Proxy traps
propagate their errors (`make({get a() { throw }}, {a: 'int'})` throws).
That is acceptable for a JSON-shaped contract but worth one sentence in the
README, since the totality claim is currently unqualified.

Fix: read props with the existing `get_own` helper (`src/make.js:134-137`,
`:147`), and use `has_own` for the `optional` check. Registry, union-option,
and enum-transform lookups already use own-property access (commit
`fe55120`); this is the one remaining inherited read.

### L1. A string registry entry crashes with a `TypeError`

```js
make(5, 'id', {id: 'str'}) // TypeError: Cannot use 'in' operator to search for 'type' in str
```

README says an entry is "a full expression, a plain object, or a function";
a bare string alias is a natural thing to write and fails with an unrelated
error instead of either working or saying "Invalid registry entry". One
line fixes it: `if (is_str(custom_type)) custom_type = {type: custom_type};`
before the `'type' in custom_type` check (`src/make.js:272`). Same spot
should reject non-object entries (`{id: 5}`) with a schema error.

### L2. Some schema errors surface as the wrong error

All are author mistakes, so severity is low, but each currently hides the
real problem:

| Input | Actual | Better |
|---|---|---|
| `{type: Symbol('q')}` | `TypeError: Cannot convert a Symbol value to a string` (from the template literal in the error message) | `Invalid type: Symbol(q)` via `String(expr.type)` |
| `{type: Object.create(null)}` | `TypeError: Cannot convert object to primitive value` | same |
| `{type: 'union', prop: 'kind'}` (no `options`) | `Union type option not found: … default=undefined` | `[type=union] should have options defined` |
| `{type: 'obj', props: …, transform: 'zz'}` | `TypeError: params.transform is not a function` | `[type=obj] transform should be a function` |
| `{type: 'tuple'}` | `[type=tuple] should have at least one option` | "…at least one item" (copy-paste from enum) |

Related: every error `make` throws is a plain `Error`, so a caller who wants
to let schema errors crash but catch the two data-dependent ones (union
without default, recursion depth) must match on message text. A `code`
property (`E_SCHEMA` / `E_DATA`) or two small subclasses would make the
"data normally does not error" rule mechanically checkable.

### L3. `engines: node >= 18` is no longer backed by the test script or CI

- `npm test` uses `--test-coverage-exclude` (Node ≥ 22.5 / 20.17) and a
  quoted glob for `--test` (Node ≥ 21). It cannot run on Node 18.
- `.github/workflows/node.js.yml` matrix is `[22.x, 24.x]`;
  [overview.md](overview.md) and [docs-packaging.md](docs-packaging.md) still
  say 18/20/22/24.
- The runtime code itself needs nothing newer than `Object.hasOwn` (16.9),
  so Node 18/20 almost certainly work — but nothing verifies it anymore.

Options: raise `engines` to `>=22` (honest, and 18 is EOL since April 2025),
or keep `>=18` and add a matrix leg that runs `node --test src/*.test.js`
without the coverage flags.

### L4. The only devDependency exists for the demo

`@vbarbarosh/node-helpers` is imported by `demos/table-columns.js` only
(`cli`, `format_date_human`, `ignore`); the tests use `node:test` and
`assert` exclusively. It brings 77 transitive packages into every
`npm ci`, which is the whole attack surface of the dev install and of the
CI run. Consider inlining the three tiny helpers into the demo (the demo
already re-implements most of its logic) and dropping the dependency, or
moving it to `optionalDependencies`-style documentation ("install to run the
demo").

### L5. Documentation precision

All examples are correct; these are places where the prose is narrower or
broader than the code:

- `is_fn_async` — README says "`async function` only", but async arrows
  (`async () => 1`) also return `true` (they share `AsyncFunction.prototype`).
  Same wording issue for `is_fn_gen`/`is_fn_gen_async` is moot (no arrow
  generators exist).
- `is_empty` — the ⚠️ mentions `Map`/`Set`, but the rule is "any object
  without own enumerable string keys", so `new Date(0)`, `/./`, and a
  `Promise` are also "empty". State the rule rather than the two examples.
- `str` — finite numbers stringify via `toString()`, so `1e21` → `'1e+21'`
  and `1e-7` → `'1e-7'`. Worth a note next to the `-0` → `'0'` remark.
- `enum` — membership uses `includes` (SameValueZero), so `-0` matches an
  option `0` and is returned as `-0` (the one place `-0` can survive), and
  `NaN` can be an option. Harmless, but the README's "returns input" is
  literally true here where `int`/`float` would normalize.
- Recursion depth — the cap is 1,024 `make` frames, which for the README's
  `node` example is 254 nested levels of input. Documenting the practical
  number lets users judge whether it applies to them.
- `nullable` on a `union` option, `optional` + `nullable` together, alias
  chains overriding `nullable` — all behave sensibly (verified) but are
  undocumented combinations; a one-line "modifiers compose" note would do.

## What was verified and is solid

- **Prototype pollution**: output objects are built with
  `Object.fromEntries` and computed-key spreads, so `__proto__` payloads
  become own data properties (pinned at `src/make.test.js:280-320`).
  Registry, union options, enum transform maps, and built-in lookups are
  all own-property reads. Registry names `constructor`/`__proto__` are
  rejected as unknown types unless explicitly defined.
- **Totality on JSON data**: with the exceptions catalogued in M1/M2, every
  JSON-shaped input to every built-in type returned a value; the only
  data-dependent throws are the documented union-without-default and the
  depth cap. The depth counter is restored after a throw (verified).
- **Idempotence**: `make(make(x, e), e)` held for every probe except the
  sparse-array case (M1) and the documented transform-cycle caveat.
- **`-0`/`NaN`/`Infinity`**: normalized exactly as the README states in
  `safe_int`, `safe_float`, `safe_str`, and the `int`/`float`/`str`/`bool`
  types; `int`/`float` `min > max` throws; out-of-range `default` is
  clamped; non-numeric `min`/`max`/`default` fall back sanely.
- **`is_fn_ctor`**: `Symbol`/`BigInt` exclusion works; Proxy-wrapped arrows
  are correctly non-constructors; no crash on non-callables.
- **Tarball**: only `README.md`, `LICENSE`, `package.json`, and the 20
  implementation files ship; tests, notes, demos, images excluded.
- **Release script**: refuses on a dirty tree, runs tests first, commits
  lockfile with the bump. Minor: it pushes the tag before `npm publish`, so
  a failed publish leaves a tag without a package; swapping the last two
  steps (publish, then push) is safer.
- **CI**: pinned `actions/checkout@v4`, `setup-node@v4`, `npm ci` with
  cache. Missing only a top-level `permissions: contents: read` block and a
  Dependabot/Renovate config — both cheap.

## Test suite

Strong, and the earned kind of 100%: the `edge_values` sweep with a `switch`
over labels forces every helper to take a position on every new value. The
gaps are exactly the ones the findings above exploit:

- No composite-type sweep: `array`, `tuple`, `tags`, `obj`, `union` are
  never fed `edge_values`, so `[,,]` (M1) and `Object.create(null)`-style
  inputs are untested there. A sweep asserting only "does not throw and is
  idempotent" for each composite type would have caught M1.
- No shorthand-with-modifier cases (M2).
- No inherited-property-name cases for `obj` props (M3); the existing
  `constructor` tests cover registry and union *keys*, not input reads.
- No string-registry-entry case (L1).
- `is_fn_ctor` still has no sweep (documented exception; fine).

Numbers in [tests.md](tests.md), [overview.md](overview.md), and
[correctness.md](correctness.md) are stale: they cite 1,337 tests, ~60 edge
values, and nyc+mocha; current is 1,622 tests, 78 edge values, `node:test`
with builtin coverage (commit `04cf14d`).
