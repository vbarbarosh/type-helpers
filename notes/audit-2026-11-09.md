## Verdict

Still in very good shape, and every fix from the September audit holds
(each is pinned by a test that passes). The suite is stronger than its
coverage number suggests: 98% of non-equivalent mutants die. This round
found three places where behavior contradicts the README — the recursion
cap does not reliably fire before the stack overflows, use-site
`before`/`after` are dropped for one kind of registry entry, and a union
option can overwrite the discriminator — plus a set of low-severity
inconsistencies and a CI matrix that has fallen one LTS behind. Nothing is
a security vulnerability in the usual sense; the package has no
dependencies and the published artifact matches the source.

## Findings

Severity is about the library's own contract (well-typed, idempotent
output; data throws only where documented), not exploitability.

### M1. The depth cap does not prevent stack overflow

`make` caps recursion at 1,024 nested `make` calls (`src/make.js:216-234`)
and README says deeper input "throws `Type recursion too deep`". For the
README's own `node` example that is true. For other ways of writing a
recursive type the JavaScript stack runs out first:

```js
let v = []; for (let i = 0; i < 1000; i++) v = [v];   // 2 kB as JSON
make(v, 'a', {a: {type: 'array', of: 'a'}});
// fresh process, Node 22.23 / 24.20 / 26.13:
//   RangeError: Maximum call stack size exceeded
```

Measured in fresh processes with the default stack size (thresholds move
by a few levels between runs):

| Recursive type written as | `make` calls per level | Cap fires at | `RangeError` first from (Node 22.23 / 24.20 / 26.13) |
|---|---|---|---|
| props shorthand: `node: {label, children: {type: 'array', of: 'node'}}` | 4 | 255 levels | never — friendly error |
| explicit: `node: {type: 'obj', props: {...}}` | 2 | ~510 levels | ~356 / ~444 / ~449 levels |
| array of itself: `a: {type: 'array', of: 'a'}` | 1 | ~1,020 levels | ~616 / ~803 / ~794 levels |
| function type calling `make` on children | 2 | ~510 levels | ~469 / friendly / friendly |

Two more effects:

- The outcome depends on JIT warm-up. In a warm process the explicit form
  accepts 500 levels; the same input overflows a cold one.
- A self-expanding type (`{a: {b: 'a'}}`) gives the friendly error from a
  shallow stack but a `RangeError` when `make` is called from roughly 2,000+
  frames deep.

Both outcomes are throws, and a throw on over-deep input is documented, so
the impact is bounded: the documented error is not the one thrown, the same
payload can pass or crash depending on warm-up, and a future `E_DATA` error
code ([improvement-plan.md](improvement-plan.md) item 3) would miss it.
The depth counter does unwind correctly after a `RangeError`.

Fix: lower `max_depth`. With 256 every form above returned the friendly
error on Node 22.23 and 26.13, including 5,000-level input and the
2,000-frames-deep case, and the suite still passes. That costs depth: about
256 array levels, 128 explicit-object levels, 64 shorthand levels. To keep the
shorthand at par, dispatch the two internal re-entries (`src/make.js:260`
and `:319`) through `make_impl` instead of `make`, so a level costs the same
in every form. Then document the limit in levels and pin it with a test
that runs in a child process.

### M2. Use-site `before`/`after` are dropped for props-shorthand registry types

When a registry entry is a plain props object, `make_impl` discards the
expression that referenced it (`src/make.js:318-319`):

```js
const types = {position: {top: 'int', left: 'int'}};
make({top: 5}, {type: 'position', after: () => 'AFTER'}, types);       // {top: 5, left: 0}
make({top: 5}, {type: 'position', before: () => ({top: 99})}, types);  // {top: 5, left: 0}
make('', {type: 'position', nullable: true, before: v => v || null}, types); // {top: 0, left: 0}
```

With `position: {type: 'obj', props: {top: 'int', left: 'int'}}` the same
three calls return `'AFTER'`, `{top: 99, left: 0}`, and `null`. The hooks
are also lost one alias away (`p3: {type: 'position', after: ...}`) and on
a union option that names the type. Only `nullable` on nullish input
survives, because it is checked before type resolution. README presents the
two registry forms as equivalent, and
[api-consistency.md](api-consistency.md) says modifiers "mean the same thing
in every expression form". No test covers a modifier on a reference to a
shorthand type.

Fix: build the `obj` expression from the registry props and merge the
use-site expression over it, the way the alias branch does:

```js
const {type: _t, optional: _o, ...use_site} = expr;
const {nullable, before, after, optional, ...props} = custom_type;
return make_impl(input, {type: 'obj', props, nullable, before, after, ...use_site}, types, [...alias_path, expr.type]);
```

### M3. A union option that declares the discriminator overwrites it

`union` returns `{[prop]: type, ...make(input, expr2, types)}`
(`src/make.js:168`), so a prop of the same name in the option wins:

```js
const expr = {type: 'union', prop: 'kind', default: 'text', options: {
    text: {kind: 'str', value: 'str'},
    num: {kind: 'raw', value: 'int'},
}};
make({kind: 'BOGUS', value: 'x'}, expr);  // {kind: 'BOGUS', value: 'x'}
make({kind: ['num'], value: 3}, expr);    // {kind: ['num'], value: 3}
make(null, expr);                         // {kind: '', value: ''}
```

README says the discriminator "is always present in the output as the
matched option key", and the code comment says raw input never leaks into
it. Listing the tag among an option's props is a natural thing to write
(it mirrors the TypeScript type). The output is then not a member of the
union, and it is not a fixed point either: the fuzzer found 361 fixed-point
violations in 200,000 cases once options may redeclare the discriminator,
and none otherwise.

Fix: `return {[prop]: type, ...make(input, expr2, types), [prop]: type};` —
the first occurrence keeps the key first, the last one sets the value. With
that change the same fuzz run has no fixed-point violations.

Related, lower severity: an option whose result is not an object is spread
anyway. An array-valued option yields `{0: …, 1: …, kind: 'a'}`, a scalar
one yields `{kind: 'a'}`, and a `nullable` option that returns `null` is
swallowed into `{kind: 'a'}`.

### L1. `optional` declared in a registry type is ignored

`obj` reads `optional` off the prop's own expression (`src/make.js:141`),
so it does not travel through a type name the way `nullable` does:

```js
make({}, {a: 'maybe'}, {maybe: {type: 'str', optional: true}});  // {a: ''}   — not omitted
make({}, {a: 'maybe'}, {maybe: {type: 'str', nullable: true}});  // {a: null} — honored
make({}, {a: {type: 'maybe', optional: true}}, {maybe: 'str'});  // {}        — honored at use site
```

Either resolve `optional` through the alias chain or state in README that
it is read only from the property's own expression.

### L2. `-0` survives `tags`

`make([-0, 0], {type: 'tags', options: [0]})` returns `[-0]`. README
documents the same SameValueZero behavior for `enum` but not for `tags`,
and [api-consistency.md](api-consistency.md) claims `-0` is normalized
"everywhere it can leak out". These two are the only non-conforming outputs
the fuzzer found. Emitting the matching option instead of
the input value fixes both types; otherwise add the note to `tags`.

### L3. `safe_int` and `safe_float` trust their bounds

The standalone helpers apply `min`/`max` without checking them:

| Call | Result |
|---|---|
| `safe_int(9, 0, 0, 5.5)` | `5.5` — not an integer |
| `safe_int(5, 0, NaN, 10)`, `safe_float(5, 0, NaN, 10)` | `NaN` |
| `safe_int(-5, 0, null, 10)`, `safe_int(50, 0, 0, null)` | `0` — `null` acts as a bound of 0 |
| `safe_int(-1, 0, -0, 5)` | `-0` |
| `safe_int(5, 0, 10, 0)` | `10` — `min` wins silently (documented in [correctness.md](correctness.md)) |

`make`'s `int`/`float` are not affected: they sanitize `min`/`max` through
`safe_int`/`safe_float` first. README's "guarantee a valid result" holds
for the helpers only when the bounds are sane numbers. Neither helper's own
test file ever passes `min` or `max`; clamping is exercised only through
`make`. Either sanitize the bounds or say they are trusted, and add direct
tests.

### L4. Schema errors are lazy, so data decides when they fire

A schema is checked only where input reaches it:

```js
make([],  {type: 'array', of: 'nope'});   // []
make([1], {type: 'array', of: 'nope'});   // Error: Invalid type: nope
make(null, {type: 'nope', nullable: true}); // null
```

The same holds for a typo inside a rarely used union option or an
`optional` prop. This is inherent to the interpreter design, but in a
request handler it turns a schema bug into an input-triggered throw that a
happy-path test never sees. A `check(expr, types)` walker (resolve every
type name, validate `options`/`items`/hooks without input) would let schema
authors fail at startup; at minimum README should say schema errors surface
on first use.

### L5. Schema strictness is uneven

Schema-author mistakes, each handled differently from its neighbor:

- A non-function `before`, `after`, or enum `transform` (`before: 'abc'`,
  `transform: 'abc'`) is silently ignored (`src/make.js:61-72`, `:331-342`);
  a non-function `obj.transform` throws.
- An array as a registry entry throws `Type defined as array`; the same
  array used directly as an expression becomes index-keyed props:
  `make([1, 2], ['int', 'str'])` → `{0: 1, 1: '2'}`.
- A sparse `tuple.items` (`[, 'int']`) produces a sparse output — the
  schema-side twin of the hole fixed in September.
- An enum transform object and the union discriminator match by string
  coercion: `make(['on'], toggle)` → `'enabled'`, and a missing
  discriminator matches an option named `undefined`. The array case is
  pinned for `union` as intentional; the `enum` side is undocumented.

### L6. `any.default` and `const.value` are handed out by reference

```js
const expr = {tags: {type: 'any', default: []}};
const a = make({}, expr), b = make({}, expr);
a.tags.push('x');   // b.tags is now ['x'] — and so is the schema's default
```

Worth one README sentence: use a function type (or `array`) when the
default must be a fresh object.

### L7. The union error echoes unbounded input

`Union type option not found: … value=<discriminator>` includes the raw
string: a 100 kB discriminator with newlines produces a 100 kB, multi-line
message. Relevant only if messages are logged or returned to clients;
truncating and JSON-quoting the value closes it.

## Tests

The suite is strong. Mutation testing changed the implementation 528 ways;
491 changes were detected. Of the 37 survivors, 28 cannot be detected by
any test because the mutated code behaves identically. Most of those mark
redundant code rather than missing tests:

- the leading `null`/`undefined`/`NaN` guard in `safe_int` and `safe_float`
  (the `typeof` switch and the later `NaN` check already cover all three);
- `Object.is(input, -0)` in `safe_str` (`(-0).toString()` is already `'0'`);
- `input === undefined` in `is_empty`.

They are harmless as statements of intent. The nine real gaps:

| Gap | Where |
|---|---|
| `min === max` on `int` and `float` (a change to `>=` would start throwing) | `src/make.js:36`, `:45` |
| `enum` with `options: []` (only the missing-`options` case is tested) | `src/make.js:57` |
| `array` without `of` on non-empty input — the documented default `raw` | `src/make.js:84` |
| `tuple` with non-array input and a `str` first item | `src/make.js:108` |
| `before` is not called for nullable `undefined` input (only `null` is pinned) | `src/make.js:251` |
| the exact depth-cap boundary | `src/make.js:224` |
| a function with its own `valueOf` passed to `safe_int`/`safe_float` (two mutants) | `src/safe_int.js:15`, `src/safe_float.js:14` |

A function carrying `valueOf` is a good `edge_values` candidate. The
`tuple` gap is covered by a README example, which is one reason to run the
README in CI (below). Beyond mutants: no test covers M2 or M3, and
`is_fn_ctor` still has no sweep (documented exception).

## CI, release, supply chain

- **Node 26 is not in the matrix.** It became LTS in October 2026;
  `.github/workflows/node.js.yml` tests 22.x and 24.x. The suite passes on
  26.13.0 locally, so adding `26.x` is free.
- **`engines` and the dev script disagree at both ends.** The code passes on
  20.20.2, `engines` says `>=22`, and `npm test` needs 22.5. Harmless for
  consumers; a contributor on 22.0–22.4 cannot run the tests.
- **README examples are not executed in CI.** They pass today (checked by
  hand in both audits). A 25-line test that extracts the `js` blocks and
  runs them would keep them honest and kills one surviving mutant.
- **CI has not run since 2026-10-02** and only runs on push/PR. The
  `ubuntu-latest` label began migrating to Ubuntu 26 on 2026-10-19, so the
  next push is likely the first run on the new image. A weekly `schedule:` trigger would surface such
  drift.
- **No provenance.** 0.4.0 was published from a workstation by
  `bin/release`; the registry entry has a signature but no attestation.
  Publishing from a tag-triggered workflow with npm trusted publishing
  (OIDC) adds provenance and removes the need for a local token.
- **Actions are pinned by major tag** (`actions/checkout@v7`,
  `actions/setup-node@v7`; both tags exist). With `permissions: contents:
  read` and no secrets the exposure is small; SHA pins maintained by
  Dependabot are the standard hardening.
- **`bin/release`** does not check the branch or that `main` is up to date
  with `origin`, so a publish can succeed and the push then fail. After a
  failed `npm publish`, a rerun bumps the version a second time. `git push
  --tags` pushes every local tag, not just the new one.
- **`bin/test` does not forward arguments.** `bin/test
  --test-name-pattern=safe_str` runs all 2,100 tests and npm warns `Unknown
  cli config`; even `npm test -- …` is ignored because the flag lands after
  the file glob.
- `cache: 'npm'` and `npm run build --if-present` are no-ops (no
  dependencies, no build script). `main` has no branch protection. There is
  no `SECURITY.md`.

## Documentation

All examples are correct. Places where the prose and the code differ:

- README:417 calls the union throw "the one case where input data … can
  throw", while the Custom types section documents the depth cap and the
  `obj` section documents getters and Proxies. [shape.md](shape.md) says
  one, [improvement-plan.md](improvement-plan.md) says two. List them once:
  union without default, recursion depth, live objects, and schema errors
  reached by data (L4).
- README:482-484 on the depth cap is accurate only for the shorthand form
  (M1).
- README:94-96: "it is treated as `{type: expr}`" is right for strings and
  functions; an object becomes `{type: 'obj', props: expr}` (the table
  below it is correct).
- `bool`: the motivating example names query params, where every value is
  a string, and `make('false', 'bool')` and `make('0', 'bool')` are `true`.
  Pinned and intentional, but it deserves a ⚠️ next to the `''` note on
  `int`.
- ESM: `import make from '@vbarbarosh/type-helpers'` works; deep imports
  need the extension (`…/src/safe_int.js`), and without it fail with
  `ERR_MODULE_NOT_FOUND`. README shows `require` only.
- The zod link (`https://zod.dev/?id=discriminated-unions`, README:411 and
  `src/make.js:149`) now redirects to the top of `zod.dev/api`; the section
  is `https://zod.dev/api#discriminated-unions`.
- Notes: [overview.md](overview.md) is headed v0.3.0 and cites
  `src/make.js:77` for the array self-hosting (now `:83`);
  [api-consistency.md](api-consistency.md) has the two claims contradicted

## What was verified and is solid

- **September fixes**: sparse-array holes, own-property reads, shorthand
  modifiers, string registry entries, and the error-message fixes are all
  pinned by passing tests and held under fuzzing.
- **Totality and idempotence of the declarative core**: 600,000 random
  schema/input pairs (nested `obj`/`union`/`array`/`tuple`, inputs drawn
  from `edge_values`, null-prototype objects, sparse arrays, prop names such
  as `__proto__`, `constructor`, `length`) produced no throw and no
  fixed-point violation, and every output had the plain-object prototype.
- **Prototype pollution**: outputs are built with `Object.fromEntries` and
  computed keys; `__proto__` payloads become own data properties.
- **Performance**: linear. 200,000 four-prop objects take 1.1–1.6 s;
  `tags` with 100,000 options and inputs takes 76 ms. There is no quadratic
  path. Sizes are unbounded by design (`str` has no length limit, `array`
  no `max`), which [shape.md](shape.md) already lists as a gap.
- **Supply chain**: zero dependencies; the published tarball is
  byte-identical to the repository's pack output and ships only `README.md`,
  `LICENSE`, `package.json`, and the 20 implementation files.
- **CJS and ESM consumption** of the packed tarball in a clean project.
